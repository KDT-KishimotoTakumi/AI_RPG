# Girls Spire Constitution

## Core Principles

### I. 仕様先行と利用者承認
すべての機能は、実装前に日本語の要件、受け入れシナリオ、境界ケース、成功基準を
`specs/` に記録しなければならない。要件化後、計画・タスク作成へ進む前に利用者の
明示的な承認を得なければならない。未確定事項を推測で実装してはならない。

### II. 決定論的で検証可能な戦術ルール
戦闘、仲間の行動解釈、自動生成、命中判定、敵AIは、同じシードと操作から同じ結果を
再現できなければならない。仲間の不確実な行動は候補・確率・危険度を事前表示し、
自滅または故意の味方攻撃を選択してはならない。合法手、射線、範囲、行動順、連携構文、
勝敗条件は表示層とAIで重複実装せず、共通ルールを正本とする。

### III. Unreal責務分離
ゲームルール、自動生成、敵AI、保存はC++の独立したドメインまたはサービスとして実装し、
表示、演出、調整値はBlueprintおよびData Assetから利用する。ルール層はUMG、入力、音声、
具体的なアセットへ依存してはならない。非同期処理には所有者、終了条件、キャンセル、
古い結果を破棄する条件を定義しなければならない。

### IV. 関係性と成人表現の安全
恋愛候補を含む全登場人物は18歳以上とし、親密表現は成人同士の合意を前提とする。
性的表現は部分的な裸体までとし、性行為を直接描写しない。該当場面には事前警告と
表示抑制設定を用意する。重要なゲーム情報を色、音、性的・恐怖演出だけに依存させず、
字幕、形状、文字、演出軽減で代替可能にしなければならない。

### V. 検証可能な完成条件
完了は、受け入れ条件を満たす自動テスト、利用可能なビルド、再現可能な手動確認、
関連資料の更新を必要とする。未実行の検証を成功扱いにしてはならない。自動生成戦場は
到達可能性、初期即死の回避、目的達成可能性を検証し、失敗時は検証済み固定戦場へ
フォールバックしなければならない。実装はテスト駆動開発で行い、失敗するテストを先に作成し、
最小実装で成功させた後にリファクタリングしなければならない。C++の行、関数、分岐の各
カバレッジは90%以上を合格条件とし、全ユーザーストーリーと主要な失敗・復旧経路を
E2Eテストで検証しなければならない。

## 技術・コンテンツ制約

- 対象はインストール済みUnreal Engine 5.7.4、Windows 11 64bit、日本語、完全オフラインとする。
  2026-09-23、利用者の「今インストールされているバージョンで作業」により変更。
- 1920×1080を基準に通常時60fps、最低30fpsを目標とし、測定環境を記録する。
- 初期版の操作はマウスのみとし、色覚対応、字幕、文字サイズ、演出軽減を提供する。
- 画像、音楽、効果音、フォント等はオリジナルまたは利用条件を記録できる素材だけを使う。
- ソースと生成物を分離し、端末固有の絶対パス、秘密情報、派生データをGit管理しない。
- 文書、画面文言、コード内コメントは日本語とする。外部ツール生成物は原文を保持する。

## 開発ワークフロー

1. `AGENTS.md` を入口、`PROAGENTS.md` を開発規約の正本として必要な資料だけを読む。
2. Speckitの順序に従い、憲章、要件、明確化、計画、チェックリスト、タスク、分析、実装を進める。
3. `docs/PLAN.md` に未着手・作業中・保留、`docs/IMPLEMENTED.md` に実装と検証の事実、
   `docs/GAME.md` に現行ゲーム仕様を記録し、同じ説明を重複させない。
4. 1変更を1目的に限定し、既存の利用者変更を保持する。破壊的操作や履歴上書きを行わない。
5. TDDを守り、ルール変更には正常系、境界条件、失敗条件、シード再現性のテストを先に追加する。
6. 仮素材で全12日を遊べる縦切り完成形を作った後、正式立ち絵と演出へ置き換える。

## Governance

本憲章は他のプロジェクト慣行より優先する。改訂には変更理由、影響する仕様・資料、移行方法、
利用者の承認を必要とする。版番号は、互換性を壊す原則変更をMAJOR、原則または節の追加を
MINOR、意味を変えない明確化をPATCHとして更新する。計画時、実装完了時、レビュー時に
憲章適合性を確認し、例外は理由と解消条件を文書化しなければならない。
